# DB 설계 기본 원칙 (Room/D1 공통)

Room이든 서버 DB(D1 등)든 관계형 DB라면 똑같이 적용되는 설계 원칙. Room 자체 API 사용법은 [android-room.md](android-room.md) 참고.

## 정규화(Normalization) — 같은 사실을 두 곳에 저장하지 않기

핵심 질문은 항상 이거다: **"이 정보, 다른 테이블에서 이미 알아낼 수 있는 거 아닌가?"** 그렇다면 중복이니 별도 컬럼/테이블 없이 지운다.

예: 판도라의 상자 앱에서 "유저 1명 = 박스 1개"로 정하고 나니, `boxes`라는 별도 테이블이 필요 없어졌다 — `photos.owner_id`만 봐도 "이 사진이 누구 박스 것인지" 이미 다 알 수 있기 때문. 별도 테이블을 계속 뒀다면 "이 박스는 누구 것인가"라는 같은 정보가 두 군데(`users`, `boxes`)에 나뉘어 저장되고, 나중에 둘이 어긋날 위험(유저는 지웠는데 박스는 안 지워짐 등)이 생긴다.

## 관계의 개수가 테이블 모양을 결정한다

- **1:N** (한 유저 : 여러 사진) — "많은 쪽"에 "적은 쪽"의 ID를 컬럼 하나로 넣으면 끝. 중간 테이블 불필요.
  ```sql
  CREATE TABLE photos (
      id TEXT PRIMARY KEY,
      owner_id TEXT NOT NULL REFERENCES users(id),  -- 이 컬럼 하나로 관계 표현 끝
      ...
  );
  ```
- **N:M** (한 유저가 여러 명한테 공유받고, 한 유저도 여러 명한테 공유해줄 수 있음) — 컬럼 하나로 표현이 안 돼서 **중간(연결) 테이블**이 필요.
  ```sql
  CREATE TABLE box_shares (
      owner_id TEXT NOT NULL REFERENCES users(id),
      viewer_id TEXT NOT NULL REFERENCES users(id),
      PRIMARY KEY (owner_id, viewer_id)
  );
  ```

**판별법**: "이쪽 하나가 저쪽 여러 개를 가질 수 있는가, 저쪽도 이쪽 여러 개를 가질 수 있는가?" 양쪽 다 "네"면 N:M, 한쪽만 "네"면 1:N.

## 제약조건(constraint) = DB가 대신 지켜주는 규칙

- **복합 기본키** (`PRIMARY KEY (owner_id, viewer_id)`): 두 컬럼의 조합이 중복되지 않도록 DB가 자동 보장. 서버 코드에서 "중복 체크" 로직을 따로 안 짜도 됨.
- **`UNIQUE`**: 특정 컬럼 값이 절대 겹치면 안 될 때 (예: `invite_code`).
- **의의**: 이런 규칙을 서버 코드의 `if`문으로도 체크할 수 있지만, DB 제약조건으로 걸어두면 코드에 버그가 있어도 DB 레벨에서 한 번 더 막아준다 — 이중 안전장치.

## 시간은 문자열이 아니라 정수(유닉스 타임스탬프)로

```kotlin
createdAt = System.currentTimeMillis()   // 1970-01-01 00:00:00 UTC부터 지난 밀리초 수
```

- **시간대(timezone) 문제가 없다**: 숫자는 어디서 봐도 절대적으로 같은 한 시점을 가리킴. 문자열로 `"2026-08-09 15:00"`이라 저장하면 이게 어느 지역 시간인지 매번 모호해짐. 표시할 때만 각 기기의 로컬 시간대로 변환하면 됨.
- 정렬/비교가 단순 숫자 비교라 빠르고 실수할 일이 없음.

## 인덱스(Index) — 책의 "찾아보기"와 같은 개념

"index"라는 단어 자체가 책 뒤의 찾아보기(색인)를 가리키는 말. 책에서 단어를 찾을 때 처음부터 다 읽는 대신 찾아보기에서 위치를 확인하고 바로 그 페이지로 가는 것과 같은 원리.

- **인덱스가 없으면**: 조건 검색(`WHERE`) 시 DB가 테이블의 모든 행을 처음부터 끝까지 훑는다(full table scan). 데이터가 적으면 문제없지만 많아지면 느려짐.
- **인덱스가 있으면**: 그 컬럼만 따로 정렬해둔 "찾아보기 표"를 DB가 미리 만들어둬서 조건에 맞는 행으로 바로 점프.
- **트레이드오프**: 인덱스는 공짜가 아님 — 데이터를 추가/수정할 때마다 그 찾아보기 표도 같이 갱신해야 해서 **쓰기(INSERT/UPDATE)가 느려지고 저장공간도 더 씀**. 그래서 자주 검색 조건으로 쓰는 컬럼에만 건다.
- **기본키(PK)는 자동으로 인덱스가 걸림** — `id`로 찾는 건 항상 빠른 이유.
- **복합 기본키의 함정**: `PRIMARY KEY (owner_id, viewer_id)`는 **앞쪽 컬럼(owner_id)으로 찾을 때만** 빠르고, `viewer_id` 하나만으로 찾을 때는 못 씀 (전화번호부가 "성"으로 정렬돼 있으면 "이름"만으로는 빨리 못 찾는 것과 같은 이치). 그래서 `viewer_id`로도 자주 찾을 거면 별도 인덱스가 필요:
  ```sql
  CREATE INDEX idx_shares_viewer ON box_shares(viewer_id);
  ```
