# 운영체제 기초 (커널)

## 커널이란

운영체제라고 하면 바탕화면, 파인더, 설정 앱까지 떠올리기 쉽지만 그건 바깥 껍데기다. 그 안쪽에 **컴퓨터가 켜져 있는 내내 돌면서 모든 걸 통제하는 핵심 프로그램 하나**가 있고, 그게 커널이다.

> **어원**: kernel은 견과류의 **알맹이**(껍질 안쪽의 먹는 부분). 짝이 되는 말이 **shell(껍데기)** 이며, 우리가 터미널에서 쓰는 zsh/bash 같은 "셸"이 바로 그 껍데기다. 사용자가 직접 만지는 바깥층 = 셸, 그 안쪽 알맹이 = 커널. 이름부터 대비되게 지어졌다.

커널이 하는 일은 크게 두 갈래다.

### ① 하드웨어 중개

앱은 디스크·네트워크 카드·메모리를 **직접 만질 수 없다.** 반드시 커널에게 요청해야 하고, 이 요청을 **시스템 콜(system call)** 이라 한다. 파일 읽기, 네트워크 연결, 메모리 할당이 전부 시스템 콜이다.

비유: 은행 창구. 손님이 금고에 직접 걸어 들어갈 수 없고, 창구 직원에게 "10만원 출금해주세요"라고 요청해야 한다. 창구 직원이 커널이고, 출금 요청이 시스템 콜이다.

### ② 자원 관리와 격리

누가 CPU를 얼마나 쓸지, 어떤 프로세스가 어떤 메모리를 볼 수 있는지, 이 사용자가 저 파일을 열 권한이 있는지 — 전부 커널이 정한다.

격리를 **커널만 할 수 있는 이유**: 앱이 스스로 "저는 이 폴더만 볼게요"라고 약속하는 건 신뢰할 수 없다. 마음먹으면 어길 수 있기 때문이다. 강제로 막을 수 있는 건 모든 요청이 반드시 거쳐 가는 창구, 즉 커널뿐이다.

## 컨테이너 격리는 ②번에 속한다

Docker 컨테이너가 쓰는 리눅스 커널 기능들은 하드웨어 접근이 아니라 자원 관리/격리 쪽이다.

- **namespace**: "이 프로세스한테는 이 파일들만, 이 프로세스 목록만, 이 네트워크만 보여줘" — 볼 수 있는 범위를 나눈다.
- **cgroup** (control group): "이 프로세스 그룹은 메모리 2GB, CPU 절반까지만" — 쓸 수 있는 양을 제한한다.

## 가상머신(VM)은 "가짜 하드웨어"를 만들어 커널을 속인다

커널은 만들어질 때부터 "내 밑에는 CPU·RAM·디스크·랜카드가 있다"고 전제하고, 부팅하면서 그것들을 찾아 초기화한다. 그래서 Mac 위에서 리눅스를 돌리는 방법은 두 가지다.

1. 리눅스 프로그램의 시스템 콜을 전부 macOS 방식으로 **번역**한다 → 수천 개를 다 번역해야 하고 미묘한 동작 차이 때문에 완벽해지기 어렵다.
2. **진짜 리눅스 커널을 그대로 하나 돌리되**, 그 커널이 기대하는 하드웨어를 소프트웨어로 만들어 눈앞에 갖다 놓는다.

VM은 2번이다. 번역이 아니라 **환경 조작**으로 커널을 속인다.

### 부품별로 무엇을 흉내 내는가

| 게스트(리눅스)가 보는 것 | 실제 정체 |
|---|---|
| 디스크 (`/dev/sda`) | 호스트 안의 **파일 하나**. "12345번 블록 읽어" → 그 파일의 해당 위치를 읽어 돌려줌 |
| RAM 8GB | 호스트가 VM에 떼어준 **메모리 영역**. 게스트의 0번지 = 실제로는 호스트 메모리의 어딘가 |
| 랜카드 | 소프트웨어로 만든 가짜 장치. 게스트가 보낸 패킷을 호스트의 진짜 네트워크로 대신 내보냄 |
| CPU | **흉내가 아님** — 진짜 CPU에서 그대로 실행된다 (아래) |

디스크가 가장 직관적이다. Docker Desktop을 깔면 Mac 어딘가에 수 GB짜리 파일이 하나 생기는데, 리눅스 입장에선 그게 하드디스크 한 개다. 리눅스는 거기 파티션을 나누고 포맷하고 파일을 만들지만, Mac 입장에선 커다란 파일 하나가 조금씩 바뀔 뿐이다.

비유: 비행 시뮬레이터. 조종사는 진짜 조종간을 당기고 계기판을 보지만 창밖은 화면이고 고도계는 계산된 값이다. 그래도 조종사는 "비행 중"이라 믿고 정상적으로 행동한다. VM 안의 커널이 그 조종사다.

### CPU는 왜 흉내 내지 않나 (요즘 VM이 느리지 않은 이유)

과거엔 CPU 명령어까지 하나하나 해석해 흉내 냈고, 그래서 VM이 매우 느렸다. 지금은 **CPU 자체에 가상화 지원 기능**이 있다. 게스트의 코드는 진짜 CPU에서 **네이티브 속도로 그대로 실행**되고, "하드웨어를 직접 만지는 특권 명령"이 나오는 순간에만 실행이 멈추고 감독 프로그램에게 제어가 넘어간다. 감독자가 가짜 응답을 만들어 돌려주면 실행이 이어진다.

그래서 VM의 손해는 계산 성능이 아니라 **부팅 시간과 메모리 점유**다.

> **어원**: 이 감독 프로그램을 **하이퍼바이저(hypervisor)** 라 한다. 예전에 OS 커널을 **supervisor**(감독자 — 프로그램들을 감독하니까)라고 불렀는데, 그 supervisor를 *또 위에서* 감독하는 존재가 생기면서 "위"를 뜻하는 hyper-를 붙인 것이다. macOS에서는 애플이 제공하는 `Hypervisor.framework`가 이 역할을 한다.

## 컨테이너 vs 가상머신(VM)

| | 커널 | 무게 | 시작 시간 | 다른 OS |
|---|---|---|---|---|
| **컨테이너** | 호스트 커널 하나를 **공유** | 수십 MB | 1초 미만 | 불가 (호스트와 같은 계열만) |
| **VM** | 가짜 하드웨어로 속여 **커널을 하나 더 부팅** | 수 GB | 수십 초 | 가능 (완전히 다른 OS도) |

컨테이너가 가벼운 이유는 커널을 새로 띄우지 않고, 이미 돌고 있는 커널에게 "얘한테는 이것만 보여줘"라고 부탁해 격리된 프로세스로만 뜨기 때문이다. 속일 하드웨어가 없으니 부팅도 없다.

**macOS/Windows에서 Docker를 쓸 때**: 공유할 리눅스 커널이 애초에 없으므로, Docker Desktop이 **VM을 하나 띄워 리눅스 커널을 마련해주고** 컨테이너들은 그 커널을 공유한다. 즉 VM 1개 + 그 안의 컨테이너 여러 개 구조다. 무거운 건 그 VM 하나뿐이고, 컨테이너는 몇 개를 띄우든 가볍다. (→ [system/docker.md](docker.md))
