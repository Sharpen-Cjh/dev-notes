판도라의 상자에서 받은 구글/Firebase 키들 — 왜, 언제, 무엇을 위해

구글 로그인과 FCM 푸시 알림을 붙이는 과정에서 여러 종류의 ID/키/JSON 파일을 받았다. 그때그때 시키는 대로 콘솔에서 값을 복사해왔지만, 각각 "무슨 문제를 풀려고 존재하는 값인지"는 따로 안 짚었다. 이 글은 그 값들이 실제로 등장한 순서대로, 각 단계에서 왜 그 값이 필요했는지를 정리한다.

FCM 자체의 개념(왜 서버가 폰에 직접 못 보내는지, 상시 연결선이 뭔지)은 push-notifications-fcm.md에 따로 있다. 여기서는 "그래서 실제로 어떤 파일/키를 받아서 어디에 썼는가"에 집중한다.

먼저: Google Cloud와 Firebase는 다른 게 아니다

이름이 달라서 별개 서비스처럼 느껴지지만, Firebase는 Google Cloud 위에 얹힌 "앱 개발자용 포장지"다. Firebase 콘솔에서 프로젝트를 하나 만들면, 뒤에서 동일한 Google Cloud 프로젝트가 하나 같이 생긴다(프로젝트 ID도 공유). 그래서 이 프로젝트에서 "구글 로그인"과 "FCM 푸시 알림"은 겉보기엔 다른 작업이었지만, 사실 같은 구글 생태계 계정 밑에서 서로 다른 제품 두 개를 쓴 것뿐이다.

1단계 — 구글 로그인을 처음 붙일 때: Android 타입 클라이언트 ID (실패)

구글은 "아무 앱이나 로그인시켜주고 사용자 정보를 내주지" 않는다. 악성 앱이 사용자를 속이는 걸 막으려고, 미리 콘솔에 앱을 등록시키고 클라이언트 ID(공개돼도 안전한 값, 비밀번호 아님)를 발급해서 "이 클라이언트 ID를 쓰는 앱한테만" 로그인을 내준다.

처음엔 Google Cloud Console에서 "Android" 타입 OAuth 클라이언트를 만들었다 — 패키지 이름(com.pandorabox.app)과 SHA-1 인증서 지문(앱을 서명하는 인증서의 고유 지문값)을 등록하는 방식. "안드로이드 네이티브 라이브러리로 직접 로그인 버튼을 붙이면 이 방식이 맞다"는 게 당시 판단이었다.

이름 유래: SHA는 Secure Hash Algorithm — 원본 데이터(여기선 인증서)를 고정 길이 지문값으로 압축하는 해시 함수 계열 이름. "1"은 그 계열의 첫 버전(지금은 취약점 때문에 보안 용도로는 대부분 SHA-256 이상을 쓰지만, 인증서 지문 식별 용도로는 아직 관례적으로 남아있다).

2단계 — 알고 보니 필요했던 건 Web 타입 클라이언트 ID

실제로 쓴 로그인 방식은 안드로이드 구버전 라이브러리가 아니라 Credential Manager API(구글이 최근 미는 통합 로그인 API)였는데, 이 API가 서버 쪽에 검증용으로 넘길 ID 토큰(serverClientId)을 받으려면 "웹 애플리케이션" 타입 클라이언트 ID가 따로 필요했다. Android 타입 클라이언트는 "이 안드로이드 앱이 맞다"는 것만 증명하는 용도라, 서버가 검증할 토큰의 대상(aud)으로 쓸 수가 없었다.

그래서 콘솔에서 Web 타입 클라이언트를 새로 만들어서: - 안드로이드 앱 (SocialLoginConfig.kt): GOOGLE_WEB_CLIENT_ID로 저장, Credential Manager에게 "이 값을 대상으로 하는 ID 토큰을 발급받아와" 라고 알려주는 용도 - 백엔드 (wrangler.jsonc의 GOOGLE_CLIENT_ID): 로그인 요청이 왔을 때 그 ID 토큰의 aud 클레임이 이 값과 일치하는지 대조하는 용도

두 값이 반드시 같아야 한다 — 다르면 "이 토큰, 우리 앱을 위해 발급된 게 맞나?" 검증에서 걸러진다(다른 앱용으로 발급된 토큰을 훔쳐써도 막아주는 게 이 대조의 역할).

참고: 여기서 JSON 파일은 등장하지 않는다 — 클라이언트 ID는 그냥 긴 문자열 하나라서 코드/설정에 직접 붙여넣으면 된다. JSON 파일이 등장하는 건 다음 FCM 단계부터다.

(비교로 참고: 카카오 로그인은 이런 aud 대조 자체가 필요 없다 — 액세스 토큰을 카카오 서버에 그대로 보내서 "유효하면 사용자 정보를 돌려준다"는 응답 성공 여부 자체가 검증이라, 애초에 다른 앱 토큰이 섞여 들어올 수가 없는 구조다. 자세한 내용은 auth-password-security.md 참고.)

3단계 — 푸시 알림을 붙이기로 함: Firebase 프로젝트 생성

FCM(Firebase Cloud Messaging)은 Firebase의 제품이라, 먼저 Firebase 콘솔에서 프로젝트를 하나 만들어야 한다. 이때부터 서로 다른 이유로 필요한 파일 두 개를 받게 되는데, 이 둘을 헷갈리지 않는 게 핵심이다.

4단계 — google-services.json: "이 앱은 어느 프로젝트 소속인가"를 앱한테 알려주는 파일

안드로이드 앱 안에 FCM SDK를 넣으면, 이 SDK가 폰 안에서 구글 서버와 상시 연결선을 만들고 이 앱 설치본을 가리키는 디바이스 토큰을 발급받아야 한다. 그런데 SDK 입장에서는 "나는 어느 Firebase 프로젝트 소속으로 등록해야 하지?"를 알 방법이 없다 — 그래서 필요한 게 google-services.json이다.

  • 내용물: 프로젝트 번호/ID, 이 앱의 패키지 이름과 매칭되는 앱 ID, API 키 등 — 전부 "이 앱이 어느 프로젝트 소속인지, 어떻게 그 프로젝트에 등록하는지"에 대한 정보다.
  • 어떻게 쓰이나: app/ 폴더에 넣어두면, 빌드할 때 com.google.gms.google-services 그레이들 플러그인이 이 내용을 앱 안에 구워 넣는다.
  • 비유: 앱이 들고 다니는 명함 같은 것 — "저는 A라는 회사 소속입니다"를 보여주는 용도지, 그 자체로 회사의 도장이나 인감(서명 권한)은 아니다.
  • 민감도: 낮다. 앱을 빌드하면 어차피 APK 안에 이 정보가 그대로 들어가서, 앱을 설치한 사람이라면 누구나 뜯어볼 수 있는 정보다. 그래도 git에는 올리지 않았다(Firebase 프로젝트가 바뀌면 다시 받아야 하는 환경별 설정 파일이라, local.properties와 같은 성격으로 취급).

5단계 — 서비스 계정 키(firebase-adminsdk-...json): "이 서버는 알림을 보낼 자격이 있는가"를 구글한테 증명하는 파일

여기가 4단계와 방향이 완전히 반대다. google-services.json은 앱이 자기 자신을 구글에게 증명하는 파일이었다면, 이 서비스 계정 키는 서버(Cloudflare Worker)가 "나는 이 프로젝트를 대신해서 메시지를 보낼 권한이 있는 소프트웨어다"를 구글에게 증명하는 용도다.

푸시를 실제로 "보내는" 주체는 사람이 아니라 우리 백엔드 서버다. 구글 입장에서는 "어느 인간 계정이 로그인했는지"가 아니라 "어느 소프트웨어가 이 프로젝트의 권한으로 API를 부르는지"를 확인해야 하는데, 이럴 때 쓰는 게 서비스 계정이다.

이름 유래("서비스 계정"): 클라우드 IAM(Identity and Access Management, 신원과 권한을 관리하는 체계) 용어. 사람이 로그인하는 "사용자 계정"과 대비해서, 프로그램/서버가 자동으로 인증받을 수 있도록 만든 계정이라는 뜻.

이 JSON 파일 안에는 두 가지 핵심 값이 들어있다: - client_email — 이 서비스 계정의 "신원"(사람으로 치면 아이디) - private_key — RSA 개인키(PEM 형식의 텍스트)

이름 유래(PEM): Privacy-Enhanced Mail. 원래 1990년대에 이메일 암호화 표준으로 만들어진 텍스트 포맷 이름인데, 그 표준 자체는 거의 안 쓰이게 됐지만 "키/인증서를 -----BEGIN ...-----로 감싸서 base64로 표현하는 텍스트 포맷" 관례만 살아남아서 지금도 인증서·키 파일 확장자로 쓰인다. 이메일과는 이제 아무 상관 없다.

이름 유래(RSA): 이 암호 방식을 고안한 세 사람 Rivest, Shamir, Adleman의 성 앞글자.

왜 이렇게 복잡한 방식이 필요한가: 우리가 우리 서버 자체 로그인 토큰에 쓰던 HMAC(대칭키 서명 — 서명할 때 쓴 비밀값과 검증할 때 쓰는 비밀값이 똑같음)과 달리, 이건 비대칭키(RSA) 서명이다. 대칭키는 "서명하는 쪽과 검증하는 쪽이 같은 편"일 때(우리 서버가 발급하고 우리 서버가 검증) 쓰기 간단하지만, 여기서는 "우리 서버가 서명하고, 남의 서버(구글)가 검증"해야 한다 — 비밀값을 공유할 수는 없으니, 개인키로 서명하고 구글은 그에 대응하는 공개키로(정확히는 구글 내부 인프라가) 검증하는 방식이 필요하다.

  • 어떻게 쓰이나: 절대 안드로이드 앱에 넣지 않는다. client_email/private_key만 뽑아서 Cloudflare Worker의 시크릿(wrangler secret put)으로 등록하고, src/fcm.ts에서 이 개인키로 JWT를 서명 → 구글 OAuth2 서버에 그 JWT를 제출하고 access token으로 교환 → 그 access token을 FCM API 호출에 실어 보낸다.
  • 민감도: 매우 높다. 이 파일을 가진 사람은 우리 서버인 척 FCM API를 부를 수 있다(다른 사람의 폰에 우리 앱 명의로 알림을 마음대로 보낼 수 있다는 뜻). 그래서 google-services.json과 정반대로 다뤘다 — 파일 자체를 절대 커밋하지 않고, 값만 뽑아 시크릿으로 등록한 뒤 원본 파일은 삭제를 권장.

이름 유래(JWT): JSON Web Token. RFC 7519라는 공식 표준으로 정의된, "이 정보(payload)를 누가 만들었는지 서명으로 증명할 수 있는 JSON 뭉치"라는 뜻 그대로의 이름.

이름 유래(OAuth): Open Authorization. "인증(authentication, 너 누구야)"이 아니라 "권한 부여(authorization, 너 이거 해도 돼)"에 초점을 맞춘 공개 표준이라는 뜻에서 이 이름이 붙었다.

6단계 — 실제로 알림 하나를 보낼 때, 이 값들이 합쳐지는 순서

  1. private_key로 JWT 서명, client_email을 발급 대상으로 명시 → 구글 토큰 발급 서버(oauth2.googleapis.com/token)에 제출
  2. 구글이 짧게(1시간) 유효한 access token 발급
  3. https://fcm.googleapis.com/v1/projects/{FCM_PROJECT_ID}/messages:send로 POST 요청 — 여기서 FCM_PROJECT_ID는 google-services.json의 project_info.project_id에서 가져온 값(비밀 아님, 그냥 "어느 프로젝트 앞으로 보내는지" 식별자)
  4. 헤더에 Authorization: Bearer {access token}, 바디에 보낼 폰의 디바이스 토큰(4단계에서 만든 google-services.json 덕분에 그 폰의 FCM SDK가 발급받은 값, 앱이 로그인 직후 서버로 보내서 DB에 저장해둔 것)을 실어 보낸다.
  5. 구글 FCM이 요청을 받아, 그 디바이스 토큰이 가리키는 폰의 상시 연결선으로 알림을 밀어넣는다.

즉 "누구를 대신해서 보내는가(서비스 계정)"와 "누구한테 보내는가(디바이스 토큰, google-services.json이 있어야 발급됨)"는 완전히 독립적인 두 갈래 정보이고, 이 둘이 4단계 요청에서 처음 만난다.
