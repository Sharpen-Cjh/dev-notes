서버리스와 Cloudflare Workers

직접 만든 라우팅 — URL 안에 변하는 값이 있을 때

프레임워크 없이 if (url.pathname === "/auth/signup")로 분기하다가, /shares/requests/{누군가의ID}/accept처럼 경로 중간에 값이 바뀌는 경우가 생기면 문자열 완전 일치로는 처리 못 한다. /로 쪼개서 위치로 꺼낸다.

const segments = url.pathname.split("/").filter(Boolean);
// "/shares/requests/abc-123/accept" → ["shares", "requests", "abc-123", "accept"]

if (segments[0] === "shares" && segments[1] === "requests" && segments[3] === "accept") {
    const viewerId = segments[2]; // 동적 부분
}

.filter(Boolean)은 경로 앞뒤의 빈 문자열(/로 시작/끝나서 생기는 빈 조각)을 걸러내는 관용구. 엔드포인트가 늘어나면 이런 수동 분기가 지저분해지는 지점이라, 이때쯤 Hono 같은 라우팅 라이브러리(/shares/requests/:viewerId/accept 처럼 패턴 문법 지원)로 옮기는 걸 고려하게 된다.

서버리스, 어떻게 아무것도 안 켜져 있는데 응답이 오는가

직관적으로 이상하게 느껴지는 질문: "요청이 없을 땐 아무것도 안 돌아간다면서, 어떻게 요청이 오면 몇 ms 만에 응답이 오지?"

답은 "아무것도 안 돌아간다"가 아니라 "손님별 전용 컴퓨터를 안 켜둔다"는 것.

  • Cloudflare는 전 세계 서버에 V8 엔진(크롬/Node.js에도 쓰이는 자바스크립트 실행 엔진)을 이미 24시간 돌리고 있다. 이건 특정 고객 전용이 아니라 Cloudflare가 운영하는 공용 인프라.
  • 배포한 코드는 미리 전 세계 서버에 복사돼있다.
  • 요청이 오면, 가까운 서버가 이미 켜져있는 V8 엔진 안에 그 코드만 순간적으로 얹어서 실행한다. 이걸 V8 isolate(격리된 실행 공간)라고 부른다.

왜 EC2 같은 가상 컴퓨터보다 훨씬 빠른가: EC2는 요청마다 컴퓨터를 켜는 게 아니라 항상 켜둔 채로 대기하는 방식이지만, 만약 매번 새로 부팅해야 한다면 운영체제 전체(커널, 드라이버 등)를 부팅해야 해서 몇 초~몇 분이 걸린다. V8 isolate는 그런 부팅 과정 자체가 없다 — 이미 켜져있는 엔진에 코드 조각 하나만 끼워 넣는 것뿐이라 몇 ms 만에 끝난다.

비유: EC2 = "나만을 위한 아파트를 통째로 빌려서 필요할 때마다 전기/수도부터 켜는 것". Workers = "이미 항상 열려있는 공용 주방에 내 주문서(코드)만 순간적으로 끼워 넣어 그 자리에서 요리 하나만 만드는 것". 주방(V8 엔진)은 다른 수천 명 것도 동시에 처리하지만, 각자의 요리(코드 실행)는 서로 안 보이게 격리(isolate)된다.

재밌는 지점: 이 기술은 브라우저에서 탭을 여러 개 열어도 서로 안 건드리고 빠르게 도는 것과 같은 원리다. Cloudflare는 브라우저 탭을 가볍게 돌리던 그 기술(V8)을, 웹페이지 대신 서버 코드를 돌리는 데 그대로 재활용했다.

"Worker"라는 이름은 어디서 왔나

리눅스의 백그라운드 데몬/윈도우 서비스랑 헷갈리기 쉬운데, 계보가 다르다.

  • 리눅스 데몬/윈도우 서비스: 요청 유무와 상관없이 항상 켜져서 대기하는 프로세스. 메모리/CPU를 계속 점유.
  • Cloudflare Worker: 평소엔 실행 중이 아니고, 요청 오는 순간에만 반짝 실행됨.

이름의 실제 유래는 자바스크립트의 Web Worker(메인 화면을 안 막고 백그라운드로 무거운 계산을 돌리는 브라우저 기능)와, 그중에서도 특히 Service Worker(네트워크 요청을 가로채서 오프라인 캐싱/푸시 알림을 구현하는 특수 워커)에서 왔다. Cloudflare Worker의 코드도 addEventListener('fetch', event => event.respondWith(...))처럼 Service Worker와 똑같은 문법을 쓴다 — "요청을 가로채서 응답한다"는 그 프로그래밍 모델을 서버 쪽으로 그대로 가져온 것.

Web Worker Service Worker
용도 무거운 계산을 메인 화면 안 막고 처리 네트워크 요청 가로채기(오프라인 캐싱 등)
생명주기 페이지에 종속(탭 닫으면 소멸) 사이트 전체에 공통, 탭 닫아도 유지 가능
fetch 가로채기 불가능 가능 (Cloudflare Worker가 본뜬 부분)

Wrangler — Cloudflare Workers의 CLI 도구

안드로이드의 gradlew(빌드/실행 담당)와 비슷한 역할을 서버 쪽에서 하는 명령어 도구.

  • wrangler dev — 배포 전에 로컬 컴퓨터에서 미리 실행/테스트
  • wrangler deploy — 실제 Cloudflare 서버에 코드를 올려 진짜 인터넷 주소로 접근 가능하게 만듦
  • wrangler d1 create / wrangler r2 bucket create — D1 DB, R2 저장소를 터미널에서 생성
  • wrangler tail — 배포된 서버의 실시간 로그 확인
  • wrangler login / logout — 로컬 컴퓨터와 Cloudflare 계정 연결. 계정 상태(예: 이메일 인증)가 바뀌었는데 CLI가 옛날 상태를 들고 있어서 에러가 나면, logout 후 login으로 세션을 새로고침하면 해결되는 경우가 많다.

이름 "Wrangler"는 원래 목장에서 가축 떼를 몰고 관리하는 사람을 뜻하는 단어. 제품 이름이 "Workers"(일꾼들)인 것과 맞물려서, "그 일꾼들을 다루는 도구"라는 말장난으로 지어졌을 가능성이 높다(Cloudflare의 공식 설명은 못 찾음, 추정).

R2의 "다운로드 무료"가 정확히 뜻하는 것

"다운로드(egress)" = R2에 저장된 파일이 인터넷을 통해 R2 밖으로 나가는 모든 행위. 예를 들어 사용자 폰이 사진을 실제로 받아올 때가 이 경우다.

  • 업로드(ingress)는 원래 AWS S3든 R2든 항상 무료였다 — 문제였던 건 항상 "꺼내갈 때(다운로드)" 쪽.
  • R2는 이 다운로드가 몇 번을 반복되든, 사용자가 몇 명이든 요금이 0원이다. AWS S3는 이 부분에 요금을 매긴다.
  • 예외: R2의 "Infrequent Access"(자주 안 쓰는 데이터용) 저장 등급은 데이터를 꺼낼 때 별도 조회 요금이 붙는다 — 이건 egress 요금이 아니라 그 저장 등급 자체의 특성.

AWS와 비교했을 때 실제로 다른 것은 "서버리스 vs 전통 서버"

Cloudflare Workers가 낯설게 느껴지는 이유는 "Cloudflare라서"가 아니라 "서버리스 방식 자체가 전통적인 서버 방식과 근본적으로 다르기 때문"이다. AWS 안에도 사실 두 모델이 다 있다:

  • EC2: 가상 컴퓨터를 통째로 빌려서 Spring 같은 걸 설치해 24시간 돌리는 전통적 방식.
  • AWS Lambda: Cloudflare Workers와 구조적으로 거의 동일한 서버리스 방식.

즉 AWS를 골랐어도 Lambda로 갔다면 똑같이 이 "낯선" 구조를 마주쳤을 것이다.
